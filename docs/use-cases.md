# Специфікації Use Case EventPass v1.0

## UC-01 «Переглянути події»

Виконавець: Компанієць Артем. Activity Diagram UC-01

| Поле | Опис |
|------|------|
| ID і назва | UC-01 «Переглянути події» |
| Мета | Дати Відвідувачу змогу переглянути доступні події, побачити їхні дані та кількість доступних квитків і за наявності місць перейти до бронювання. |
| Основний актор | Відвідувач |
| Тригер | Відвідувач хоче обрати подію, на яку можна забронювати квиток. |
| Передумови | Система доступна. |
| Основний сценарій | 1. Відвідувач відкриває розділ з подіями.<br>2. Система показує список доступних подій.<br>3. Відвідувач обирає подію зі списку.<br>4. Система показує назву, дату, місце та кількість доступних квитків обраної події.<br>5. Система перевіряє, чи є доступні квитки.<br>6. Система дозволяє перейти до бронювання (UC-03). |
| Альтернативні та виняткові потоки | A1. Крок 5: доступних квитків немає (AvailableSeats = 0) - система повідомляє, що бронювання недоступне; сценарій завершується без бронювання. |
| Постумови | Успіх: Відвідувач бачить дані обраної події, і йому дозволено перейти до бронювання. Невдача (A1): перехід до бронювання недоступний; дані в системі не змінено. |
| Пов'язані вимоги | FR-01; NFR-01 |
| Критерії приймання | AC-01.1, AC-01.2, AC-01.3, AC-01.4; AC-N1.1 |

## UC-02 «Створити подію»

Виконавець: Лобуренко Вікторія. Activity Diagram UC-02

| Поле | Опис |
|------|------|
| ID і назва | UC-02 «Створити подію» |
| Мета | Додати до системи нову подію із вказаною локацією та кількістю квитків, яка не перевищує місткість локації. |
| Основний актор | Організатор |
| Тригер | Організатор має намір створити нову подію. |
| Передумови | Система доступна; локація проведення події відома Організатору. |
| Основний сценарій | 1. Організатор обирає кнопку «Створити подію».<br>2. Організатор вводить в поля назву, дату, опис, локацію та кількість квитків.<br>3. Організатор натискає «Зберегти».<br>4. Система перевіряє коректність введених даних.<br>5. Система перевіряє, що кількість квитків не перевищує місткість локації.<br>6. Система створює подію Event.<br>7. Система встановлює AvailableSeats, що дорівнює кількості квитків.<br>8. Система зберігає подію.<br>9. Система показує підтвердження. |
| Альтернативні та виняткові потоки | A1. Крок 4: обов'язкове поле не заповнене або дані некоректні - система повідомляє про помилку, подію не створює; сценарій завершується з помилкою.<br>A2. Крок 5: кількість квитків більша за місткість локації - система повідомляє про помилку, подію не зберігає; сценарій завершується з помилкою. |
| Постумови | Успіх: подію створено та збережено, AvailableSeats дорівнює кількості квитків. Невдача (A1, A2): подію не створено, дані в системі не змінено. |
| Пов'язані вимоги | FR-02 |
| Критерії приймання | AC-02.1, AC-02.2, AC-02.3, AC-02.4 |

## UC-03 «Забронювати квиток»

Виконавець: Мельник Олександр. Activity Diagram UC-03

| Поле | Опис |
|------|------|
| ID і назва | UC-03 «Забронювати квиток» |
| Мета | Забронювати вказану кількість квитків на обрану подію, списати місця й видати Відвідувачу квиток з унікальним токеном і QR-кодом. |
| Основний актор | Відвідувач |
| Тригер | Відвідувач обрав подію з доступними квитками (UC-01) і хоче її забронювати. |
| Передумови | Подію обрано; для неї є доступні квитки (UC-01). |
| Основний сценарій | 1. Відвідувач обирає подію та кількість квитків.<br>2. Відвідувач натискає кнопку «Забронювати».<br>3. Система перевіряє кількість доступних місць.<br>4. Система встановлює, що вільних місць достатньо, і створює бронювання (Order).<br>5. Система записує статус бронювання в BookingHistory.<br>6. Система зменшує кількість доступних місць події на обрану кількість квитків.<br>7. Система створює квиток з унікальним токеном і статусом Valid.<br>8. Система генерує QR-код.<br>9. Система показує підтвердження та квиток. |
| Альтернативні та виняткові потоки | A1. Крок 3: вільних місць недостатньо (запитана кількість більша за залишок) - система повідомляє про причину відмови; бронювання й квиток не створюються, кількість місць не змінюється, запис у BookingHistory не додається; сценарій завершується з помилкою. |
| Постумови | Успіх: бронювання створено, статус записано в BookingHistory, кількість доступних місць зменшено, квиток зі статусом Valid і унікальним токеном створено. Невдача (A1): бронювання, квиток і запис в BookingHistory не створено, кількість місць не змінено. |
| Пов'язані вимоги | FR-03, FR-04, FR-06; NFR-02 |
| Критерії приймання | AC-03.1, AC-03.2, AC-03.3; AC-04.1, AC-04.2, AC-04.3, AC-04.4; AC-06.1, AC-06.2; AC-N2.1, AC-N2.2 |

## UC-04 «Перевірити квиток»

Виконавець: Коляда Анастасія. Activity Diagram UC-04

| Поле | Опис |
|------|------|
| ID і назва | UC-04 «Перевірити квиток» |
| Мета | Перевірити дійсність квитка за токеном, позначити дійсний квиток використаним і не допустити повторного проходу. |
| Основний актор | Контролер |
| Тригер | Відвідувач пред'являє квиток із QR-кодом на вході на подію. |
| Передумови | Квиток створено (UC-03); Контролер має токен квитка з QR-коду. |
| Основний сценарій | 1. Контролер вводить токен квитка з QR-коду.<br>2. Контролер натискає «Перевірити».<br>3. Система шукає квиток за токеном і знаходить його.<br>4. Система перевіряє, що статус квитка Valid.<br>5. Система підтверджує дійсність квитка.<br>6. Система змінює статус квитка на Scanned.<br>7. Система показує результат перевірки. |
| Альтернативні та виняткові потоки | A1. Крок 3: квиток за введеним токеном не знайдено - система повідомляє, що квиток не знайдено або він недійсний; сценарій завершується з помилкою.<br>A2. Крок 4: статус квитка не Valid - система повідомляє, що квиток уже використано, повторний прохід не допускається; сценарій завершується з помилкою. |
| Постумови | Успіх: квиток має статус Scanned, Контролер бачить результат перевірки. Невдача (A1, A2): статус квитка не змінено. |
| Пов'язані вимоги | FR-05; NFR-01 |
| Критерії приймання | AC-05.1, AC-05.2, AC-05.3, AC-05.4; AC-N1.2 |
