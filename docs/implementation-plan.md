# План реалізації EventPass v1.0

Технологічний стек: серверна частина - ASP.NET Core Web API (C#) з Entity Framework Core і MySQL; клієнтська частина - React (JavaScript), що працює з API через HTTP/JSON.

| Етап | Зміст | Залежить від | Результат і перевірка | Відповідальний |
|------|-------|--------------|-----------------------|----------------|
| 0. Каркас і база даних | Solution ASP.NET Core Web API і окремий React-застосунок; підключення MySQL через EF Core; сутності та схема за Class Diagram (users, events, orders, tickets, booking_history), довідник локацій із місткістю; міграції EF Core; початкові дані (користувачі з ролями, локації); налаштування CORS; узгоджений контракт API (ендпоінти та формат відповідей) | — | Міграція створює схему в MySQL; тестові дані завантажуються; React-застосунок успішно викликає тестовий ендпоінт API | Уся команда |
| 1. Створення події | UC-02: FR-02. API: `POST /api/events` з перевіркою коректності даних і кількості квитків щодо місткості локації, AvailableSeats = кількість квитків. React: форма «Створити подію» з показом помилок | Етап 0 (Event посилається на локацію) | AC-02.1–AC-02.4; модульні тести перевірок; прогін Activity UC-02 за всіма гілками | Мельник |
| 2. Перегляд подій | UC-01: FR-01. API: `GET /api/events`, `GET /api/events/{id}`. React: список подій, сторінка події з кількістю доступних квитків, кнопка переходу до бронювання лише за AvailableSeats > 0 | Етапи 0–1 (потрібні збережені події) | AC-01.1–AC-01.4; прогін Activity UC-01 за обома гілками | Коляда |
| 3. Бронювання і квиток | UC-03: FR-03, FR-04, FR-06, NFR-02. API: `POST /api/bookings`. Одна транзакція: створення Order, запис у BookingHistory, зменшення AvailableSeats, створення Ticket з криптографічно випадковим токеном (статус Valid), генерація QR-коду; захист від овербукінгу токеном конкурентності (RowVersion) або блокуванням рядка події. React: вибір кількості квитків, показ підтвердження і QR-коду | Етап 1-2 (потрібна подія з AvailableSeats), UI | AC-03.1–AC-03.3, AC-04.1–AC-04.4, AC-06.1–AC-06.2; інтеграційний тест паралельного бронювання (AC-N2.1–AC-N2.2); прогін Activity UC-03 за обома гілками | Лобуренко |
| 4. Перевірка квитка і стани | UC-04: FR-05, FR-07. API: `POST /api/tickets/validate` (пошук за токеном, перехід Valid → Scanned, відхилення повторного проходу); скасування замовлення з переходом Valid → Cancelled. Усі переходи State Machine Ticket зібрані в одному сервісі статусів. React: форма введення токена та показ результату | Етап 3 (квитки мають існувати) | AC-05.1–AC-05.4, AC-07.1–AC-07.2; тести кожного дозволеного й недозволеного переходу; прогін Activity UC-04 за всіма гілками | Компанієць |
| 5. Інтеграція і перевірка | Наскрізний сценарій (створити подію → переглянути → забронювати → перевірити квиток), вимір часу відповіді API (NFR-01), тест паралельного бронювання останніх місць (NFR-02); Sequence Diagram за фактичним кодом | Етапи 1–4 | AC-01.1–AC-07.2, AC-N1.1–AC-N2.2; оновлена RTM з посиланнями на код і тести | Уся команда |

Послідовність визначено залежностями моделей. Event посилається на локацію, тому довідник локацій створюється на етапі 0. Бронювання неможливе без події з AvailableSeats, тому створення події (етап 1) іде раніше за бронювання. Ticket створюється під час бронювання, тому перевірка квитка (етап 4) іде після етапу 3. Усі переходи State Machine зібрані в одному сервісі статусів, щоб правила Valid → Scanned і Valid → Cancelled не дублювалися. Контракт API узгоджується на етапі 0, щоб React-частина та серверна частина кожного етапу могли розроблятися паралельно. Після завершення етапу 1 етапи 2 і 3 можна виконувати паралельно, оскільки обидва спираються лише на збережені події. Перехід від перегляду до бронювання в інтерфейсі підключають, щойно будуть готові обидва етапи. Етап 5 виконується останнім, бо перевіряє систему в зборі та доповнює RTM фактичною реалізацією й результатами тестів.
